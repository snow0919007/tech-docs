Workers 最佳实践

来自生产实践、Cloudflare 内部用法与社区常见问题的 Workers 建议。

最佳实践 原文更新于 2026-10-12 对应页面：best-practices/workers-best-practices

这些最佳实践基于生产环境中的实际模式、Cloudflare 自身内部的用法，以及开发者社区里常见的问题。

配置

让兼容性日期保持最新

compatibility_date 决定你的 Worker 能用哪些运行时特性与缺陷修复。新项目把它设为当天日期，可以拿到最新行为；老项目定期更新，无需改代码就能获得新的 API 与修复。

{
	"name": "my-worker",
	"main": "src/index.ts",
	"upload_source_maps": true,
	// Set this to today's date
	"compatibility_date": "2026-11-02",
	"compatibility_flags": ["nodejs_compat"],
}
name = "my-worker"
main = "src/index.ts"
upload_source_maps = true
# Set this to today's date
compatibility_date = "2026-11-02"
compatibility_flags = [ "nodejs_compat" ]

详见兼容性日期。

启用 nodejs_compat

nodejs_compat 兼容性标志让 Worker 能使用 Node.js 内置模块，如 node:crypto、node:buffer、node:stream 等。许多库依赖这些模块；开启该标志可以避免运行时出现难以理解的导入错误。

	"name": "my-worker",

	// Set this to today's date

启用 source map

为每个 JavaScript 或 TypeScript Worker 启用 source map。这样捕获到的异常堆栈会指向你的原始文件与行号。

{
  "$schema": "./node_modules/wrangler/config-schema.json",
  "upload_source_maps": true
}
upload_source_maps = true

如果由框架或自定义构建工具打包你的 Worker，记得在其服务端构建中也开启外部 source map。用 Vite 时，配置 Worker 环境的 build.sourcemap。注意别把服务端 map 混进公开静态资源。

用 wrangler types 生成绑定类型

不要手写 Env 接口。运行 wrangler types，生成与实际 Wrangler 配置一致的类型定义文件。这样，配置与代码不匹配的问题会在编译期而不是部署时才暴露。

每次新增或重命名绑定后，重新运行一次 wrangler types。

npx wrangler types
yarn wrangler types
pnpm wrangler types
// ✅ Good: Env is generated by wrangler types and always matches your config
// Do not manually define Env — it drifts from your actual bindings

export default {
	async fetch(request, env) {
		// env.MY_KV, env.MY_BUCKET, etc. are all correctly typed
		const value = await env.MY_KV.get("key");
		return new Response(value);
	},
};
// ✅ Good: Env is generated by wrangler types and always matches your config
// Do not manually define Env — it drifts from your actual bindings

	async fetch(request: Request, env: Env): Promise<Response> {
		// env.MY_KV, env.MY_BUCKET, etc. are all correctly typed

用 wrangler secret 存密钥，不要写进源码

密钥（API key、令牌、数据库凭据）绝不能出现在 Wrangler 配置或源码里。用 wrangler secret put 安全存放，运行时通过 env 访问。本地开发用 .env 文件，并确保它写进了 .gitignore。详见环境变量。

认真规划环境（Environments）

Wrangler 环境让你把同一份代码部署成生产、预发、开发三套独立的 Worker。每个环境会创建一个名为 {name}-{env} 的独立 Worker（例如 my-api-production 与 my-api-staging）。

每个环境是分开处理的：绑定与变量必须按环境分别声明，不会继承。参见不可继承的键。根 Worker（不带环境后缀）是另一次独立部署；如果你不打算用它，就别在不指定 --env 的情况下部署。

{
	"name": "my-api",
	"main": "src/index.ts",
	"upload_source_maps": true,
	// Set this to today's date
	"compatibility_date": "2026-11-02",
	"compatibility_flags": ["nodejs_compat"],

	// This binding only applies to the root Worker
	"kv_namespaces": [{ "binding": "CACHE", "id": "dev-kv-id" }],

	"env": {
		// Production environment: deploys as "my-api-production"
		"production": {
			"kv_namespaces": [{ "binding": "CACHE", "id": "prod-kv-id" }],
			"routes": [
				{ "pattern": "api.example.com/*", "zone_name": "example.com" },
			],
		},
		// Staging environment: deploys as "my-api-staging"
		"staging": {
			"kv_namespaces": [{ "binding": "CACHE", "id": "staging-kv-id" }],
			"routes": [
				{ "pattern": "api-staging.example.com/*", "zone_name": "example.com" },
			],
		},
	},
}

正确设置自定义域名或路由

Workers 支持两种路由机制，用途不同：

  • 自定义域名：Worker 就是源站。Cloudflare 会自动创建 DNS 记录与 SSL 证书。当这个 Worker 要处理某个主机名的全部流量时用它。
  • 路由（Routes）：Worker 运行在现有源站之前。添加路由前，该主机名必须已有一条经 Cloudflare 代理（橙云）的 DNS 记录。

路由最常见的错误就是漏了 DNS 记录。没有代理的 DNS 记录，对该主机名的请求会返回 ERR_NAME_NOT_RESOLVED，永远到不了 Worker。如果你没有真实源站，可以加一条指向 100:: 的代理 AAAA 记录作为占位。

{
	"name": "my-worker",
	"main": "src/index.ts",
	"upload_source_maps": true,
	// Set this to today's date
	"compatibility_date": "2026-11-02",
	"compatibility_flags": ["nodejs_compat"],

	// Option 1: Custom domain — Worker is the origin, DNS is managed automatically
	"routes": [{ "pattern": "api.example.com", "custom_domain": true }],

	// Option 2: Route — Worker runs in front of an existing origin
	// Requires a proxied DNS record for shop.example.com
	// "routes": [
	// 	{ "pattern": "shop.example.com/*", "zone_name": "example.com" }
	// ]
}
name = "my-worker"
main = "src/index.ts"
upload_source_maps = true
# Set this to today's date

请求与响应处理

用流处理请求体与响应体

无论内存上限是多少，流式处理大请求与大响应在任何语言里都是最佳实践：它能降低内存峰值、改善首字节时间。Workers 有 128 MB 内存上限，所以用 await response.text() 或 await request.arrayBuffer() 把整个响应体读进内存，遇到大载荷会直接把 Worker 打挂。

对于确实要整体消费的请求体（JSON 载荷、文件上传），请在读取之前强制限定最大体积，避免客户端送来你并不想处理的数据。

用 TransformStream 让数据流经你的 Worker，从源头送向目的地，而不必全部驻留内存。

// 🔴 Bad: buffers the entire response body in memory
const badHandler = {
	async fetch(request, env) {
		const response = await fetch("https://api.example.com/large-dataset");
		const text = await response.text();
		return new Response(text);
	},
};

// ✅ Good: stream the response body through without buffering
export default {
	async fetch(request, env) {
		const response = await fetch("https://api.example.com/large-dataset");
		return new Response(response.body, response);
	},
};
// 🔴 Bad: buffers the entire response body in memory
const badHandler = {
	async fetch(request: Request, env: Env): Promise<Response> {
		const response = await fetch("https://api.example.com/large-dataset");
		const text = await response.text();
		return new Response(text);
	},
} satisfies ExportedHandler<Env>;

export default {
	async fetch(request: Request, env: Env): Promise<Response> {
		const response = await fetch("https://api.example.com/large-dataset");

当需要拼接多个响应（例如从几个上游 API 取数据）时，把每个响应体依次管道写入同一个可写流，这样任何一个响应都不必驻留内存。

export default {
	async fetch(request, env) {
		const urls = [
			"https://api.example.com/part-1",
			"https://api.example.com/part-2",
			"https://api.example.com/part-3",
		];

		const { readable, writable } = new TransformStream();

		// ✅ Good: pipe each response body sequentially without buffering
		const pipeline = (async () => {
			for (const url of urls) {
				const response = await fetch(url);
				if (response.body) {
					// pipeTo with preventClose keeps the writable open for the next response
					await response.body.pipeTo(writable, {
						preventClose: true,
					});
				}
			}
			await writable.close();
		})();

		// Return the readable side immediately — data streams as it arrives
		return new Response(readable, {
			headers: { "Content-Type": "application/octet-stream" },
		});
	},
};
export default {
	async fetch(request: Request, env: Env): Promise<Response> {
		const urls = [

			"https://api.example.com/part-3",

响应之后的工作交给 waitUntil

ctx.waitUntil() 让你在响应已发给客户端之后继续做事，例如埋点、写缓存、记日志或发 webhook。这样响应保持快速，后台任务也照样完成。

只用 ctx.waitUntil() 处理不影响响应的工作。如果响应依赖于这项工作，就在返回响应前 await 它，或随着工作进展流式输出响应。注意：如果 Worker 还在流式发送响应体，即使不用 ctx.waitUntil() 也仍处于活跃状态。

两个常见坑：一是解构 ctx（会丢失 this 绑定，抛出 "Illegal invocation"）；二是在响应已发送或客户端已断开后，超过 waitUntil() 的 30 秒时限。

// 🔴 Bad: destructuring ctx loses the `this` binding
const badHandler = {
	async fetch(request, env, ctx) {
		const { waitUntil } = ctx; // "Illegal invocation" at runtime
		waitUntil(fetch("https://analytics.example.com/events"));
		return new Response("OK");
	},
};

// ✅ Good: send the response immediately, do background work after
export default {
	async fetch(request, env, ctx) {
		const data = await processRequest(request);

		ctx.waitUntil(logToAnalytics(env, data));
		ctx.waitUntil(updateCache(env, data));

		return Response.json(data);
	},
};

async function logToAnalytics(env, data) {
	await fetch("https://analytics.example.com/events", {
		method: "POST",
		body: JSON.stringify(data),
	});
}

async function updateCache(env, data) {
	await env.CACHE.put("latest", JSON.stringify(data));
}

架构

用绑定访问 Cloudflare 服务，而不是 REST API

R2、KV、D1、Queues、Workflows 等 Cloudflare 服务都提供绑定。绑定是进程内的直接引用：无需网络跳转、无需鉴权、不增加额外延迟。在 Worker 里调 REST API 既费时又添不必要的复杂度。

// 🔴 Bad: calling the REST API from a Worker
const badHandler = {
	async fetch(request, env) {
		const response = await fetch(
			"https://api.cloudflare.com/client/v4/accounts/ACCOUNT_ID/r2/buckets/BUCKET_NAME/objects/my-file",
			{ headers: { Authorization: `Bearer ${env.CF_API_TOKEN}` } },
		);
		return new Response(response.body);
	},
};

// ✅ Good: use the binding directly — no network hop, no auth needed
export default {
	async fetch(request, env) {
		const object = await env.MY_BUCKET.get("my-file");

		if (!object) {
			return new Response("Not found", { status: 404 });
		}

		return new Response(object.body, {
			headers: {
				"Content-Type":
					object.httpMetadata?.contentType ?? "application/octet-stream",
			},
		});
	},
};
// 🔴 Bad: calling the REST API from a Worker
const badHandler = {
	async fetch(request: Request, env: Env): Promise<Response> {

异步与后台工作交给 Queues 和 Workflows

长时间运行、可重试或非紧急的任务不应阻塞请求。用 Queues ↗ 与 Workflows ↗ 把工作移出关键路径。两者用途不同：

需要把生产者与消费者解耦时，用 Queues。Queues 是消息代理：一个 Worker 发消息，另一个 Worker 稍后处理。它适合扇出（一个事件触发多个消费者）、缓冲与批处理（把消息聚合后再写入下游服务）、以及简单的单步后台任务（发邮件、触发 webhook、写日志）。Queues 提供至少一次（at-least-once）投递，并支持按消息配置重试。

后台工作由多个相互依赖的步骤组成时，用 Workflows。Workflows 是持久化执行引擎：每一步的返回值都会被持久化，某一步失败只重试那一步，而不是整个任务。它适合多步流程（扣款、创建发货、发送确认）、需要暂停与恢复的长时间任务（等 Hours 或数天的外部事件，或通过 step.waitForEvent() 等人工审批）、以及后续步骤依赖前面结果的复杂条件逻辑。Workflows 可以运行数小时、数天乃至数周。

两者一起用：当高吞吐入口要喂给复杂处理时。例如让 Queue 缓冲进来的订单，而消费者为每个需要多步履约的订单创建一个 Workflow 实例。

export default {
	async fetch(request, env) {
		const order = await request.json();

		if (order.type === "simple") {
			// ✅ Queue: single-step background job — send a message for async processing
			await env.ORDER_QUEUE.send({
				orderId: order.id,
				action: "send-confirmation-email",
			});
		} else {
			// ✅ Workflow: multi-step durable process — payment, fulfillment, notification
			const instance = await env.FULFILLMENT_WORKFLOW.create({
				params: { orderId: order.id },
			});
		}

		return Response.json({ status: "accepted" }, { status: 202 });
	},
};
export default {
	async fetch(request: Request, env: Env): Promise<Response> {
		const order = await request.json<{ id: string; type: string }>();

Worker 之间通信用服务绑定

一个 Worker 要调用另一个 Worker 时，用服务绑定，而不是向公网 URL 发 HTTP 请求。服务绑定零成本、绕过公网，并支持类型安全的 RPC。

import { WorkerEntrypoint } from "cloudflare:workers";

// The "auth" Worker exposes RPC methods
export class AuthService extends WorkerEntrypoint {
	async verifyToken(token) {
		// Token verification logic
		return { userId: "user-123", valid: true };
	}
}

// The "api" Worker calls the auth Worker via a service binding
export default {
	async fetch(request, env) {
		const token = request.headers.get("Authorization")?.replace("Bearer ", "");

		if (!token) {
			return new Response("Unauthorized", { status: 401 });
		}

		// ✅ Good: call another Worker via service binding RPC — no network hop
		const auth = await env.AUTH_SERVICE.verifyToken(token);

		if (!auth.valid) {
			return new Response("Invalid token", { status: 403 });
		}

		return Response.json({ userId: auth.userId });
	},
};
import { WorkerEntrypoint } from "cloudflare:workers";

// The "auth" Worker exposes RPC methods
export class AuthService extends WorkerEntrypoint {
	async verifyToken(
		token: string,
	): Promise<{ userId: string; valid: boolean }> {
		// Token verification logic
		return { userId: "user-123", valid: true };
	}
}

// The "api" Worker calls the auth Worker via a service binding
export default {
	async fetch(request: Request, env: Env): Promise<Response> {
		const token = request.headers.get("Authorization")?.replace("Bearer ", "");

		if (!token) {
			return new Response("Unauthorized", { status: 401 });
		}

			return new Response("Invalid token", { status: 403 });
		}

		return Response.json({ userId: auth.userId });
	},
} satisfies ExportedHandler<Env>;

连外部数据库用 Hyperdrive

从 Worker 连远程 PostgreSQL 或 MySQL 时，始终使用 Hyperdrive ↗。Hyperdrive 会在靠近你数据库的地区维护连接池，省掉每个请求的 TCP 握手、TLS 协商与连接建立成本，并在可能时缓存查询结果。

WebSocket 用 Durable Objects

普通 Worker 也能把 HTTP 连接升级为 WebSocket，但它缺乏持久状态与休眠能力。一旦 isolate 被驱逐，连接就断了，因为没有持久的 actor 来维持它。要做可靠的长期 WebSocket 连接，请用 Durable Objects ↗ 配合休眠 API（Hibernation API）↗。Durable Objects 即使对象被驱逐出内存也能保持 WebSocket 连接，并在消息到达时自动唤醒。

要启用休眠，请用 this.ctx.acceptWebSocket() 而不是 ws.accept()。用 setWebSocketAutoResponse 处理 ping/pong 心跳，避免唤醒对象。

import { DurableObject } from "cloudflare:workers";

// Parent Worker: upgrades HTTP to WebSocket and routes to a Durable Object
export default {
	async fetch(request, env) {
		if (request.headers.get("Upgrade") !== "websocket") {
			return new Response("Expected WebSocket", { status: 426 });
		}

		const stub = env.CHAT_ROOM.getByName("default-room");
		return stub.fetch(request);
	},
};

// Durable Object: manages WebSocket connections with hibernation
export class ChatRoom extends DurableObject {
	constructor(ctx, env) {
		super(ctx, env);
		// Auto ping/pong without waking the object
		this.ctx.setWebSocketAutoResponse(
			new WebSocketRequestResponsePair("ping", "pong"),
		);
	}

	async fetch(request) {
		const pair = new WebSocketPair();
		const [client, server] = Object.values(pair);

		// ✅ Good: acceptWebSocket enables hibernation
		this.ctx.acceptWebSocket(server);

		return new Response(null, { status: 101, webSocket: client });
	}

	// Called when a message arrives — the object wakes from hibernation if needed
	async webSocketMessage(ws, message) {
		for (const conn of this.ctx.getWebSockets()) {
			conn.send(typeof message === "string" ? message : "binary");
		}
	}

	async webSocketClose(ws, code, reason, wasClean) {
		// With web_socket_auto_reply_to_close (compat date >= 2026-04-07), the runtime
		// auto-replies to Close frames. Calling close() is safe but no longer required.
		ws.close(code, reason);
	}
}

代码模式

不要把请求级状态存在全局作用域

Worker 会在多个请求之间复用 isolate。某个请求里设置的变量，在下一个请求里依然存在。这会导致跨请求数据泄漏、状态过期，以及 "Cannot perform I/O on behalf of a different request" 错误。

把状态通过函数参数传递，或保存在 env 的绑定里。绝不要放在模块级变量中。

// 🔴 Bad: global mutable state leaks between requests
let currentUser = null;

const badHandler = {
	async fetch(request, env, ctx) {
		// Storing request-scoped data globally means the next request sees stale data
		currentUser = request.headers.get("X-User-Id");
		const result = await handleRequest(currentUser, env);
		return Response.json(result);
	},
};

// ✅ Good: pass request-scoped data through function arguments
export default {
	async fetch(request, env, ctx) {
		const userId = request.headers.get("X-User-Id");
		const result = await handleRequest(userId, env);

		return Response.json(result);
	},
};

async function handleRequest(userId, env) {
	return { userId };
}

Promise 要么 await，要么交给 waitUntil

既没有 await、也没有 return、也没传给 ctx.waitUntil() 的 Promise，就是「漂浮的 Promise（floating promise）」。它会造成静默的 bug：结果被丢弃、错误被吞掉、工作没做完。Workers 运行时可能在这个 Promise 完成之前就终止你的 isolate。

怎么处理取决于响应是否依赖这项工作：必须完成后响应才正确的，用 await 或 return；可以在响应发出之后再跑、且能在 waitUntil() 时限内完成的，用 ctx.waitUntil()。

打开 no-floating-promises 规则，在开发期就抓出这类问题。用 ESLint 就启用 @typescript-eslint/no-floating-promises ↗；用 oxlint 就启用 typescript/no-floating-promises ↗。

# oxlint
npx oxlint --deny typescript/no-floating-promises src/

				method: "POST",

		return new Response("OK");
	},

安全

用 Web Crypto 生成安全令牌

Workers 运行时提供 Web Crypto API 做密码学操作。唯一标识用 crypto.randomUUID()，随机字节用 crypto.getRandomValues()。任何涉及安全的场景都不要用 Math.random()，它不是密码学安全的。

开启 nodejs_compat 后 Node.js 的 node:crypto 也完全受支持，用你或你的库更习惯的那个即可。

export default {
	async fetch(request, env) {
		// 🔴 Bad: Math.random() is predictable and not suitable for security
		const badToken = Math.random().toString(36).substring(2);

		// ✅ Good: cryptographically secure random UUID
		const sessionId = crypto.randomUUID();

		// ✅ Good: cryptographically secure random bytes for tokens
		const tokenBytes = new Uint8Array(32);
		crypto.getRandomValues(tokenBytes);
		const token = Array.from(tokenBytes)
			.map((b) => b.toString(16).padStart(2, "0"))
			.join("");

		return Response.json({ sessionId, token });
	},
};

比较密钥值（API key、令牌、HMAC 签名）时，用 crypto.subtle.timingSafeEqual() 防止计时侧信道攻击。不要在长度不一致时提前短路返回；先把两个值都编码成固定长度的哈希再比。

async function verifyToken(provided, expected) {
	const encoder = new TextEncoder();

	// ✅ Good: hash both values to a fixed size, then compare in constant time
	// This avoids leaking the length of the expected value
	const [providedHash, expectedHash] = await Promise.all([
		crypto.subtle.digest("SHA-256", encoder.encode(provided)),
		crypto.subtle.digest("SHA-256", encoder.encode(expected)),
	]);

	return crypto.subtle.timingSafeEqual(providedHash, expectedHash);
}

// 🔴 Bad: direct string comparison leaks timing information
function verifyTokenInsecure(provided, expected) {
	return provided === expected;
}

		await env.MY_KV.put("key", "value");
		const result = await env.MY_KV.get("key");
		expect(result).toBe("value");
	});

	it("should return null for missing keys", async () => {
		const result = await env.MY_KV.get("nonexistent");
		// ✅ Good: test the null case explicitly
		expect(result).toBeNull();
	});
