兼容性日期

用日期选定一个 Workers 运行时版本，决定 Worker 会看到哪些行为。

配置 原文更新于 2026-04-23 对应页面：configuration/compatibility-dates

Cloudflare 会定期更新 Workers 运行时。这些更新全局生效，正常情况下绝不该让已部署的 Worker 停止工作。但有时某些改动会不向后兼容——尤其是运行时 API 里本来就有 bug，而已有 Worker 可能不经意地依赖了这些 bug。Cloudflare 的做法是：修好 bug，新 Worker 可以选择接受修复后的行为，而已有 Worker 继续看到带 bug 的旧行为，以免破坏已部署的服务。

兼容性日期与兼容性标志，就是开发者用来选择是否接受这些运行时变化的手段。兼容性标志通常会有一个「默认启用」的日期，因此只要给 Worker 指定 compatibility_date，你就能一次性启用截至该日期（含该日期）的所有这类标志。

设置兼容性日期

项目刚起步时，compatibility_date 应当始终设为当天日期。之后应偶尔更新它。更新时，请查阅兼容性标志页面弄清哪些行为变了，并务必测试你的 Worker 是否受影响，必要时改代码。新的兼容性日期会在你下次运行 npx wrangler deploy 时生效。

不想更新也完全可以不更新——Workers 运行时会永久支持旧的兼容性日期。如果 Cloudflare 因为某些原因认为必须做一次会破坏线上 Worker 的改动，会主动联系受影响的开发者。当然，Cloudflare 会尽可能避免这种情况。

不过，即便不必更新 compatibility_date，保持更新仍是好习惯，原因有两点：

  1. 有时新特性只对使用当前 compatibility_date 的 Worker 开放。想用上最新特性，就得跟上日期。
  2. 一般来说，除了兼容性标志页面之外，Workers 文档只描述当前 compatibility_date 下的行为，不会保留历史行为的说明。如果你的 Worker 用的是旧日期，就需要反复翻兼容性标志页，确认你用到的 API 有没有变过。

通过 Wrangler

兼容性日期可以在 Worker 的 Wrangler 配置文件里设置：

{
	// Opt into backwards-incompatible changes through April 5, 2022.
	"compatibility_date": "2022-04-05"
}
compatibility_date = "2022-04-05"

通过 Cloudflare 控制台

在 Cloudflare 控制台创建 Worker 时，兼容性日期会自动设为当天日期。

之后可以在 Cloudflare 控制台 ↗的 Workers 设置里更新兼容性日期。

通过 Cloudflare API

用 Workers Script API ↗ 或 Workers Versions API ↗ 上传 Worker 时，可以在请求体的 metadata 字段里设置兼容性日期。

注意默认值

通过 API 上传时如果没指定兼容性日期，默认取最老的日期——即任何标志生效之前（2021-11-02）。通过 API 新建 Worker 时，强烈建议把兼容性日期设为当天日期。
