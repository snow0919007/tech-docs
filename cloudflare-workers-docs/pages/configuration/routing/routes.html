路由（Routes）

把 URL 模式映射到 Worker，只让匹配的请求跑你的代码。

配置 原文更新于 2026-10-18 对应页面：configuration/routing/routes

背景

路由（Routes）让你把 URL 模式映射到某个 Worker。当抵达 Cloudflare 网络的请求匹配指定 URL 模式时，你的 Worker 就会在这条路由上执行。

路由是一组针对请求 URL 进行求值的规则。如果你有一台需要始终与之通信的指定应用服务器，推荐用路由：对入站 Request 对象调用 fetch()，就会向该应用服务器发起子请求——目标由 Cloudflare 区域的 DNS 设置决定。

路由为你在 Cloudflare 上已代理的主机名（在应用服务器之前）加上 Workers 能力，让 Worker 充当代理，在访问 Cloudflare 后面的应用服务器之前先完成必要的工作。

原站示意图

原文此处配有一张图，说明路由与你在 Cloudflare DNS 中定义的应用之间的关系。

路由可以对自定义域名发起 fetch()，并且当同一主机名上两者都配置时，路由优先。例如你想在应用前面跑一个记日志的 Worker，就可以给应用 Worker 在 app.example.com 上建自定义域名，再给日志 Worker 建一条 app.example.com/* 的路由：调用 fetch() 就会调起自定义域名上的应用 Worker。注意，路由不能作为同区 fetch() 调用的目标。

设置路由

要添加路由，你需要：

  1. 一个处于活跃状态的 Cloudflare 区域 ↗；
  2. 一个可被调用的 Worker；
  3. 为你要路由到的域名或子域配置好的 DNS 记录，并且该记录经 Cloudflare 代理（即橙云代理）。
谨慎

路由的配置方式取决于是不是你应用的源站。如果 Worker 就是你应用的源站，请改用自定义域名。

如果 Worker 不是应用源站，按下面的步骤设置路由。

注意

路由也可以通过 API 创建，详见 Workers Routes API ↗。

在控制台设置路由

设置之前，先确认你要路由到的域名或子域已有 DNS 记录。

  1. 在 Cloudflare 控制台进入 Workers & Pages。前往 Workers & Pages ↗
  2. 在 Overview 中选择你的 Worker。
  3. 进入 Settings > Domains & Routes > Add > Route。
  4. 选择区域并填入路由模式。
  5. 选择 Add route。

在 Wrangler 配置文件中设置路由

同样，先确认要路由到的域名或子域已有 DNS 记录。Wrangler 配置文件里的写法如下：

{
	"routes": [
		{
			"pattern": "subdomain.example.com/*",
			"zone_name": "example.com"
		},
		// or
		{
			"pattern": "subdomain.example.com/*",
			"zone_id": "<YOUR_ZONE_ID>"
		}
	]
}
[[routes]]
pattern = "subdomain.example.com/*"
zone_name = "example.com"

[[routes]]
pattern = "subdomain.example.com/*"
zone_id = "<YOUR_ZONE_ID>"

每条路由后面都要加 zone_name 或 zone_id，两者可以互换。用 zone_id 时，这样找：

  1. 在 Cloudflare 控制台打开该区域的 Overview 页面。前往 Overview ↗
  2. 在 Overview 页面左侧找到 Zone ID。

添加多条路由：

{
	"routes": [
		{
			"pattern": "subdomain.example.com/*",
			"zone_name": "example.com"
		},
		{
			"pattern": "subdomain-two.example.com/example",
			"zone_id": "<YOUR_ZONE_ID>"
		}
	]
}
[[routes]]
pattern = "subdomain.example.com/*"
zone_name = "example.com"

[[routes]]
pattern = "subdomain-two.example.com/example"
zone_id = "<YOUR_ZONE_ID>"

匹配行为

路由模式长这样：

https://*.example.com/images/*

这个模式会匹配所有发往 example.com 的某个子主机、且路径以 /images/ 开头的 HTTPS 请求。

要匹配所有请求，模式写成：

*example.com/*

虽然看起来像正则 ↗，但路由模式遵循的是一套专门规则：

  • 唯一支持的运算符是通配符 *，匹配零个或多个任意字符。
  • 路由模式不能包含中缀通配符或查询参数。例如 example.com/*.jpg 与 example.com/?foo=* 都不是合法的路由模式。
  • 当多个模式都能匹配某个请求 URL 时，最具体的模式胜出。例如匹配 https://www.example.com/ 时，www.example.com/* 优先于 *.example.com/*；匹配 example.com/hello/world 时，example.com/hello/* 优先于 example.com/*。
  • 匹配会把整个请求 URL（包括查询字符串）纳入考量。由于路由模式不能含查询参数，想让模式匹配带查询参数的 URL，唯一办法是用通配符 * 收尾。
  • 路由模式的路径部分区分大小写，例如 example.com/Images/* 与 example.com/images/* 是两条不同的路由。
  • 2023 年 10 月 15 日之前创建的路由，其模式中主机部分区分大小写，例如 example.com/* 与 Example.com/* 是两条不同的路由。
  • 2023 年 10 月 15 日及之后创建的路由，主机部分不区分大小写，example.com/* 与 Example.com/* 等价。

一条路由可以不绑定任何 Worker——它的作用是「排除」更宽泛的模式。例如这一对模式，一个带脚本、一个不带：

*example.com/images/cat.png -> <no script>
*example.com/images/*       -> worker-script

在这个例子里，所有发往 example.com 且路径以 /images/ 开头的请求都会走 worker-script，唯独 /images/cat.png 例外——它会完全绕过 Workers。而 /images/cat.png?foo=bar 因为带了查询字符串，仍会被路由到 worker-script。

合法性规则

下面这些规则决定路由模式是否合法。

模式必须包含你的区域

如果你的区域是 example.com，最简单的模式就是 example.com，它只匹配 http://example.com/ 与 https://example.com/，别的一概不匹配。与 URL 一样，不写路径时隐含路径为 /。

不能包含查询参数

例如 https://example.com/?anything 不是合法的路由模式。

可以可选地以 http:// 或 https:// 开头

省略协议时，会同时匹配 http:// 与 https://；写了 http:// 就只匹配 HTTP，写了 https:// 就只匹配 HTTPS。

  • https://*.example.com/ 匹配 https://www.example.com/，但不匹配 http://www.example.com/。
  • *.example.com/ 两者都匹配。

主机名可以可选地以 * 开头

模式的主机名以 * 开头时，匹配该主机及其所有子主机；以 *. 开头时，只匹配所有子主机。

  • *example.com/ 匹配 https://example.com/ 与 https://www.example.com/。
  • *.example.com/ 匹配 https://www.example.com/，但不匹配 https://example.com/。
谨慎

因为 * 匹配的是任意字符（不只是子域部分）的零次或多次出现，*example.com 会匹配任何以 example.com 结尾的主机名，包括 myexample.com 与 not-example.com。若只想匹配 example.com 及其子域，请写两条路由：example.com/* 与 *.example.com/*。

下面这张表说明 *example.com/* 与 *.example.com/* 的差别：

请求 URL*example.com/**.example.com/*
https://example.com/匹配不匹配
https://www.example.com/path匹配匹配
https://myexample.com/匹配不匹配
https://not-example.com/匹配不匹配
区域范围

Cloudflare 只在你创建路由的那个区域内求值 Workers 路由。就普通区域路由而言，某个模式匹配并不代表 myexample.com、not-example.com 这类无关域名会去用 example.com 区域的路由——上表只是演示通配符的字符串匹配行为。

Cloudflare for SaaS 的自定义主机名 ↗则可以把流量送经服务商自己的区域，在那里按该区域的 Workers 路由求值。

这个区分对区域内的子域模式很关键：例如 example.com 区域里的 *sub.example.com/* 会匹配 sub.example.com、foo.sub.example.com 与 notsub.example.com。

请求 URL*sub.example.com/**.sub.example.com/*
https://sub.example.com/匹配不匹配
https://foo.sub.example.com/path匹配匹配
https://notsub.example.com/匹配不匹配

路径可以可选地以 * 结尾

模式的路径以 * 结尾时，匹配该路径的所有后缀：

  • https://example.com/path* 匹配 https://example.com/path、https://example.com/path2 与 https://example.com/path/readme.txt。
谨慎

路径匹配在通配符 * 与正斜杠 / 上有一个已知 bug，记录在已知问题中。

域名与子域必须有 DNS 记录

所有域名与子域都必须有 DNS 记录，才能经 Cloudflare 代理并用它调用 Worker。例如你想把 Worker 放到 myname.example.com，而 example.com 已接入 Cloudflare、却没有为 myname.example.com 添加任何 DNS 记录，那么发往该主机名的请求都会以 ERR_NAME_NOT_RESOLVED 失败。

谨慎

如果你之前用 Cloudflare 控制台为 example.com 下的 myname 添加过指向 100::（保留的 IPv6 丢弃前缀 ↗）的 AAAA 记录，Cloudflare 建议改为创建一个指向 Worker 的自定义域名。
