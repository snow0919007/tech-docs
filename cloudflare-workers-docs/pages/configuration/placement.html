部署位置（Placement）

让 Worker 跑在离后端更近的地方，而不是离用户更近的地方。

配置 原文更新于 2026-10-12 对应页面：configuration/placement

默认情况下，Workers 与 Pages Functions 运行在离请求接收地最近的数据中心。但如果你的 Worker 需要请求数据库、API 这类后端基础设施，那么把 Worker 放在离后端更近而不是离终端用户更近的位置，性能可能更好。

{
	"placement": {
		// Use one of the following options (mutually exclusive):
		"mode": "smart", // Cloudflare automatically places your Worker closest to the upstream with the most requests
		"region": "gcp:us-east4", // Explicit cloud region to run your Worker closest to - e.g. "gcp:us-east4" or "aws:us-east-1"
		"host": "db.example.com:5432", // A host to probe (TCP/layer 4) - e.g. a database host - and place your Worker closest to
		"hostname": "api.example.com", // A hostname to probe (HTTP/layer 7) - e.g. an API endpoint - and place your Worker closest to
	},
}
[placement]
mode = "smart"
region = "gcp:us-east4"
host = "db.example.com:5432"
hostname = "api.example.com"

Placement 通过最小化 Worker 与后端服务之间的往返延迟，降低一次 Worker 请求的整体耗时。对跑在传统云基础设施上的数据库、API 与其他服务，可以做到个位数毫秒的延迟。

选项适用场景配置
Smart多个后端服务，或不清楚基础设施位置mode = "smart"
Region单个后端服务，且位于已知云区域region
Host单个后端服务，且不在主流云厂商host 或 hostname

理解 Placement

设想一位悉尼的用户访问跑在 Workers 上的应用，而这个应用要多次往返访问位于法兰克福的数据库。

悉尼与法兰克福之间多次往返的延迟会叠加。把 Worker 放到数据库附近，Cloudflare 就能缩短请求总时长。

原站示意图

原文此处有两张对比图：未启用 Smart Placement 时，Worker 在用户所在区域、每次查询都要跨洲往返数据库；启用后，Worker 被放到法兰克福（数据库所在处），用户只承受一次跨洲往返。

启用 Smart Placement

Smart Placement 会自动分析 Worker 的流量模式，把它放到最优位置。适合这些情况：

  • Worker 连接多个后端服务；
  • 你不清楚基础设施的确切位置；
  • 后端服务是分布式或有多副本的。

Smart Placement 按 Worker 单独启用。启用后，它会定期分析该 Worker 在不同 Cloudflare 节点上的请求耗时。

对每个候选位置，Smart Placement 会权衡 Worker 在该处的表现与转发请求带来的网络延迟。如果某个候选位置明显更快，就把请求转发过去；否则 Worker 仍在离请求最近的默认位置运行。

Smart Placement 只考虑该 Worker 曾经运行过的位置，无法把它放到通常收不到流量的节点。

限制

  • Smart Placement 只影响 fetch 事件处理器的执行，不影响 RPC 方法或命名入口点。
  • 没有 fetch 事件处理器的 Worker 会被 Smart Placement 忽略。
  • 静态资源始终从离入站请求最近的节点提供；如果你的代码通过静态资源绑定取资源，则从 Worker 运行的节点提供。

启用 Smart Placement

所有 Workers 套餐都可使用 Smart Placement。

用 Wrangler 配置

{
	"placement": {
		"mode": "smart",
	},
}
[placement]
mode = "smart"

部署后，Smart Placement 最长可能需要 15 分钟来分析你的 Worker。

在控制台配置

  1. 进入 Workers & Pages。前往 Workers & Pages ↗
  2. 选择你的 Worker。
  3. 进入 Settings > General。
  4. 在 Placement 下选择 Smart。

Smart Placement 需要 Worker 有来自多个地点的稳定流量才能做出决策，分析过程最长可能需要 15 分钟。

查看部署位置状态

通过 Workers API 查询该 Worker 的 placement 状态：

curl -X GET https://api.cloudflare.com/client/v4/accounts/$ACCOUNT_ID/workers/services/$WORKER_NAME \
-H "Authorization: Bearer $CLOUDFLARE_API_TOKEN" \
-H "Content-Type: application/json" | jq .

可能的状态：

状态说明
（无该字段）尚未分析该 Worker，它跑在离请求最近的默认位置。
SUCCESS已分析完成，Smart Placement 会对它做优化。
INSUFFICIENT_INVOCATIONS来自多个地点的请求量不足以做出放置决策。
UNSUPPORTED_APPLICATIONSmart Placement 反而让 Worker 变慢，已回退原放置。这种情况很少见（不足 1% 的 Worker）。

查看请求耗时分析

启用 Smart Placement 后，系统会采集请求耗时数据。耗时是在离终端用户最近的数据中心测量的。默认有 1% 的请求不走 Smart Placement，用作对比基线。

查看 Worker 的请求耗时分析，衡量 Smart Placement 的实际效果。

查看 cf-placement 响应头

启用 placement 后，Cloudflare 会给所有请求加上 cf-placement 头。可以用它判断某个请求是否走了 Smart Placement、以及 Worker 在哪里处理了这个请求。

该头的值包含放置类型与表示数据中心位置的机场代码：

  • remote-LHR：请求经 Smart Placement 路由到伦敦附近的数据中心。
  • local-EWR：请求未走 Smart Placement，Worker 在纽瓦克附近的默认位置运行。
谨慎

在 Smart Placement 退出 beta 之前，cf-placement 头可能会被移除。

配置显式的 Placement Hints

Placement Hints 让你明确指定 Worker 在哪里运行。适合这些情况：

  • 你知道后端基础设施的确切位置；
  • Worker 只连接一个数据库、API 或服务；
  • 你的基础设施是单点部署的（没有副本，也不是 anycast）。

典型例子是某个区域里的一台主数据库、一台虚拟机或一个 Kubernetes 集群。把每次查询的往返延迟从 20～30 毫秒降到 1～3 毫秒，响应时间会有明显改善。

注意

Workers 运行在 Cloudflare 的全球网络 ↗上，而不是云厂商的区域内部。Placement Hints 会把 Worker 放到离你指定云区域延迟最低的数据中心。在极高请求量下（每秒数十万次以上），Cloudflare 可能会把实例分散到更大范围的节点上以平衡流量。

指定云区域

如果你的基础设施跑在 AWS、GCP 或 Azure 上，用 {provider}:{region} 格式设置 placement.region：

{
	"placement": {
		"region": "aws:us-east-1", // Explicit cloud region to run your Worker closest to - e.g. "gcp:us-east4" or "aws:us-east-1"
	},
}
[placement]
region = "aws:us-east-1"

Cloudflare 会把指定的云区域映射到离它延迟最低的数据中心，并自动根据网络维护或变化调整放置，你不需要额外指定故障转移区域。

指定主机端点

如果你的基础设施不在主流云厂商，可以给 Cloudflare 一个可探测的端点。Cloudflare 会三角定位这台外部主机的方位，把 Worker 放到附近区域。

注意

基于主机（host）的放置属于实验性功能。

用 placement.host 指定第 4 层服务。Cloudflare 通过 TCP CONNECT 探测测量延迟，选出最优数据中心。

{
	"placement": {
		"host": "my_database_host.com:5432", // A host to probe (TCP/layer 4) - e.g. a database host - and place your Worker closest to
	},
}
[placement]
host = "my_database_host.com:5432"

用 placement.hostname 指定第 7 层服务。Cloudflare 通过 HTTP HEAD 探测测量延迟，选出最优数据中心。

{
	"placement": {
		"hostname": "my_api_server.com", // A hostname to probe (HTTP/layer 7) - e.g. an API endpoint - and place your Worker closest to
	},
}
[placement]
hostname = "my_api_server.com"

探测来自公网 IP 段，而不是 Cloudflare 的 IP 段。Cloudflare 会定期重新检查服务位置。这些探测用于定位单点部署的资源，对广播、anycast、组播或多副本资源并不适用。

支持的云区域

Placement Hints 支持 Amazon Web Services（AWS）、Google Cloud Platform（GCP）与 Microsoft Azure 的区域标识：

厂商格式示例

Placement 行为

无论用 Smart Placement 还是 Placement Hints，Worker 的放置行为都相似。以下说明对两者都适用。

限制

  • Placement 只影响 fetch 事件处理器的执行，不影响 RPC 方法或命名入口点；没有 fetch 事件处理器的 Worker 会被忽略。
  • 静态资源始终从离入站请求最近的节点提供；若通过静态资源绑定取资源，则从 Worker 运行处提供。

cf-placement 响应头

启用 placement 后，Cloudflare 会给所有请求加上 cf-placement 头，用于判断请求是否经 placement 路由、以及 Worker 在何处处理它。remote-LHR 表示经 Smart Placement 路由到伦敦附近；local-EWR 表示未走 placement，在纽瓦克附近运行。

谨慎

在 Smart Placement 退出 beta 之前，cf-placement 头可能会被移除。

多 Worker 架构

在 Workers 上构建全栈应用时，把边缘逻辑（认证、路由）与后端逻辑（数据库查询、API 调用）拆成不同的 Worker，并用服务绑定以类型安全的 RPC 连接它们。

把 placement 配在后端 Worker 上，让它靠近数据库执行；边缘 Worker 则在离用户近的地方完成认证。

import { AppWorker } from "../app-worker/src/index";

interface Env {
	APP: Service<AppWorker>;
}

export default {
	async fetch(request: Request, env: Env): Promise<Response> {
		const authHeader = request.headers.get("Authorization");
		if (!authHeader?.startsWith("Bearer ")) {
			return new Response("Unauthorized", { status: 401 });
		}

		const userId = await validateToken(authHeader.slice(7));
		if (!userId) {
			return new Response("Invalid token", { status: 403 });
		}

		// Call the placed back-end Worker via RPC
		const data = await env.APP.getUser(userId);
		return Response.json(data);
	},
};

async function validateToken(token: string): Promise<string | null> {
	return token === "valid" ? "user-123" : null;
}

import { WorkerEntrypoint } from "cloudflare:workers";

export default class AppWorker extends WorkerEntrypoint {
	async fetch() {
		return new Response(null, { status: 404 });
	}

	// Each method runs near your database - multiple queries stay fast
	async getUser(userId: string) {
		const user = await this.env.DB.prepare("SELECT * FROM users WHERE id = ?")
			.bind(userId)
			.first();
		return user;
	}

	async getUserListings(userId: string) {
		// Multiple round-trips to the DB are low-latency when placed nearby
		const user = await this.env.DB.prepare("SELECT * FROM users WHERE id = ?")
			.bind(userId)
			.first();
		const listings = await this.env.DB.prepare(
			"SELECT * FROM listings WHERE owner_id = ?",
		)
			.bind(userId)
			.all();
		const reviews = await this.env.DB.prepare(
			"SELECT * FROM reviews WHERE listing_id IN (SELECT id FROM listings WHERE owner_id = ?)",
		)
			.bind(userId)
			.all();

		return { user, listings: listings.results, reviews: reviews.results };
	}
}

auth-worker 跑在边缘，快速拒绝未授权请求；已认证的请求通过 RPC 转发给 app-worker，后者靠近数据库运行，查询更快。

Durable Objects

Durable Objects ↗ 无需配置就能自动放置。对 Durable Object 内置 SQLite 数据库 ↗ 的查询几乎零延迟 ↗——因为计算与数据在同一进程内。

尽量把工作放在 Durable Object 内部一次做完、返回组合结果，而不是从 Worker 里多次往返：

import { DurableObject } from "cloudflare:workers";

type Session = { id: string; user_id: string; created_at: number };
type PromptHistory = {
	id: string;
	session_id: string;
	role: string;
	content: string;
};

export class AgentHistory extends DurableObject {
	async getSessionContext(sessionId: string) {
		// All queries execute with zero network latency — compute and data are colocated
		const session = this.ctx.storage.sql
			.exec<Session>("SELECT * FROM sessions WHERE id = ?", sessionId)
			.one();
		const prompts = this.ctx.storage.sql
			.exec<PromptHistory>(
				"SELECT * FROM prompt_history WHERE session_id = ? ORDER BY created_at",
				sessionId,
			)
			.toArray();

		return { session, prompts };
	}
}
