Cloudflare Access 保护

在请求抵达 Worker 之前先验身份：让指定的人进来，其他人挡在门外。

配置 原文更新于 2026-10-12 对应页面：configuration/cloudflare-access

借助 Cloudflare Access，你可以限定谁有权访问自己的应用。由你决定放行谁，且每个请求都会在你的 Worker 运行之前被校验：通过的访问者被放行，其余人被带到登录页或直接拦下。

可以保护的范围：

  • 单个应用：要求访问其预览 URL、生产 URL 或两者都要登录。
  • 账户下所有 Worker：默认保护现存与将来新建的所有 Worker。
  • 特定自定义域名与主机名：在主机名或路由层面限制访问。

准备工作

要在 Workers 上使用 Access，你需要：

  • 账户已启用 Zero Trust。若尚未开启，请先完成 Zero Trust 设置 ↗，再回到 Workers 控制台。
  • 具备管理 Workers 与 Access 应用的权限。

保护所有 Worker

要求账户下每个 Worker（包括你将来部署的）都先登录。可以只要求预览部署登录，也可以生产与预览都要求。

控制台路径：Workers & Pages 概览页 > Protect all Workers。

  1. 在 Cloudflare 控制台进入 Workers & Pages。前往 Workers & Pages ↗
  2. 找到 Protect all Workers 卡片。
  3. 如果卡片显示 Not enabled，选择 Enable Access。
  4. 选择 Previews only（仅预览）或 All traffic（全部流量）。
  5. 在 Authentication policy 下选择已有策略，或配置下文策略选项之一。
  6. 选择 Enable Access。
  7. （可选）查看会话时长。
  8. 选择 Apply Access。

如果只想保护所有 Worker 的预览部署，创建一个目标类型为 all_preview_workers 的自托管 Access 应用：

"destinations": [
  {
    "type": "all_preview_workers"
  }
]

要保护每个 Worker 的生产与预览部署，改用 all_workers：

"destinations": [
  {
    "type": "all_workers"
  }
]

把这些 destinations 放进 POST /accounts/{account_id}/access/apps 请求。完整请求结构（含策略选项、会话设置与进阶 Access 选项）见 Access applications API ↗。

保护单个 Worker

要求单个 Worker 先登录。这会自动保护与该 Worker 关联的所有域名，包括它的路由、自定义域名、workers.dev 主机名与预览。可以只要求预览部署登录，也可以生产与预览都要求。

WebSocket 限制

Worker 级 Access 策略目前不支持 WebSocket 连接。对受 Worker 级策略保护的 Worker 发起 WebSocket 升级请求，会以 403 失败。

如果你的 Worker 用到 WebSocket（包括 Durable Objects、实时应用或基于 WebSocket 的 RDP），请改用基于主机名的 Access 应用来保护。

控制台路径：Workers & Pages > 选择你的 Worker > Access。

  1. 在 Cloudflare 控制台进入 Workers & Pages。前往 Workers & Pages ↗
  2. 从应用列表中选择你的 Worker。
  3. 选择 Access 标签页。
  4. 选择 Protect this Worker behind Access。
  5. 选择 Previews only 或 All traffic。
  6. 在 Authentication policy 下选择已有策略，或配置策略选项。
  7. （可选）查看会话时长。
  8. 选择 Apply Access。

如果只想保护单个 Worker 的预览部署，创建目标类型为 preview_worker 的自托管 Access 应用，并把 worker_id 设为该 Worker 的 ID：

curl "https://api.cloudflare.com/client/v4/accounts/$ACCOUNT_ID/access/apps" \
  --request POST \
  --header "Authorization: Bearer $CLOUDFLARE_API_TOKEN" \
  --json '{
    "type": "self_hosted",
    "name": "Access for my-worker",
    "destinations": [
      {
        "type": "preview_worker",
        "worker_id": "c81a2d22c29840ed9d61681a3270dbff"
      }
    ],
    "policies": [
      {
        "decision": "allow",
        "include": [
          {
            "email_domain": {
              "domain": "example.com"
            }
          }
        ]
      }
    ]
  }'

要连同生产部署一起保护，把目标类型改成 worker：

"destinations": [
  {
    "type": "worker",
    "worker_id": "c81a2d22c29840ed9d61681a3270dbff"
  }
]

完整请求结构见 Access applications API ↗。

保护特定主机名、自定义域名或路径

当只有某个路由到 Worker 的特定 URL 需要登录时（例如某个 workers.dev 主机名、某个自定义域名、子域或路径），用基于主机名的 Access。它只保护那一个确切 URL；而保护整个 Worker则不管通过什么方式访问都会生效。例如用主机名方式，你可以只保护 my-worker.example.workers.dev、admin.example.com，或 example.com/login 这一个路径，从而只让 Worker 的一部分变成私有。

无论在控制台还是 API，保护主机名或路径的方式都是创建一个自托管应用 ↗，并把该主机名或路径作为应用域名。

在 Zero Trust > Access > Applications 中创建自托管应用。要匹配子域、多路径或通配符，见应用路径 ↗。

也可以用 POST /accounts/{account_id}/access/apps 请求创建，把应用域名设为主机名或路径。完整请求结构见 Access applications API ↗。

在所有 Worker 受保护时让某个 Worker 公开

如果账户级 Access 保护了所有 Worker，你可以为某个 Worker 添加 Worker 级旁路（bypass），让它变为公开——旁路意味着 Access 不再要求该 Worker 登录。

注意

这仅在账户级 Access 已经保护该 Worker 时才有意义。若没有账户级 Access 策略，公开的 Worker 本就无需旁路。

控制台路径：Workers & Pages > 选择你的 Worker > Access。

  1. 在 Cloudflare 控制台进入 Workers & Pages。前往 Workers & Pages ↗
  2. 从应用列表中选择你的 Worker。
  3. 选择 Access 标签页。
  4. 选择把该 Worker 设为公开、或绕过账户级 Access 的选项。
  5. 确认改动。

用 API 的做法是创建一个带旁路策略的 Worker 级 Access 应用：用 worker 目标、把 worker_id 设为该 Worker 的 ID，并把策略 decision 设为 bypass，include 规则匹配所有人：

"policies": [
  {
    "decision": "bypass",
    "include": [
      {
        "everyone": {}
      }
    ]
  }
]

策略选项

开启 Access 时，要选择谁能登录。无论保护所有 Worker 还是单个 Worker，可选的策略都一样。

策略选项结果
Cloudflare 账户允许该 Cloudflare 账户的成员登录。当你希望访问仅限已属于该账户的人时使用。
邮箱域名允许任何在你填入的域名（如 example.com）下拥有已验证邮箱的人登录。当你希望某公司或组织的人都能访问、即便他们不是 Cloudflare 账户成员时使用。

可以添加一条或多条策略；匹配任一被选中策略的访问者即可登录。

若需要进阶策略配置（多个身份提供方、设备状态规则、服务令牌、复杂策略排序、自定义登录页或拦截页），在创建之后到 Zero Trust 里编辑该 Access 应用。完整选项见Access 策略 ↗。

用 ctx.access 读取已认证的用户身份

当 Cloudflare Access 对一次直接调用你的 Worker的请求完成认证后，Worker 可以通过 ctx.access 读取已登录用户的身份——包括邮箱、用户组、设备状态，以及更多身份字段 ↗。无需额外配置，也不用自己解析 JWT。

可以用它做响应个性化、细粒度权限控制，或按用户记录活动。

如果 Access 并未对该请求完成认证，ctx.access 为 undefined。

export default {
	async fetch(request, env, ctx) {
		if (!ctx.access) {
			return new Response("Access required", { status: 403 });
		}

		const identity = await ctx.access.getIdentity();
		const email = identity?.email ?? "unknown";

		return new Response(`Hello, ${email}`);
	},
};

ctx.access 的限制

注意

ctx.access 只作用于被 Access 认证的那一次 Worker 调用。Cloudflare Access 不会把 ctx.access 透过服务绑定的 HTTP 请求或 RPC 调用传递下去——下游 Worker 收不到调用方的 Access 上下文。

如果调用方改为向受 Access 保护的主机名发起 fetch() 子请求，并带上有效的服务令牌头 ↗或有效的 CF_Authorization cookie ↗，Access 会重新评估这个新请求，并为下游 Worker 创建一个新的 ctx.access。那是新认证的上下文，不是从调用方传过来的上下文。

使用静态资源的 Worker 运行在一个内部路由 Worker 之后。Access 仍然保护应用及其资源，但该路由不会把 ctx.access 传给用户 Worker。

当输入的 Wrangler 配置里没有 assets 时，Cloudflare Vite 插件会把它补进生成的部署配置。因此使用该插件的框架（包括 TanStack Start）即使源码配置没有声明静态资源，也可能受到影响。

本地测试 ctx.access

用 wrangler dev 或 Cloudflare Vite 插件本地开发时，可以模拟已通过 Cloudflare Access 认证的身份，而无需部署或走一遍登录流程。

在 wrangler.jsonc 的 access 配置里加一个 dev 块：

{
	"access": {
		"dev": {
			"aud": "my-app",
			"identity": { "email": "admin@example.com" }
		}
	}
}
[access.dev]
aud = "my-app"

  [access.dev.identity]
  email = "admin@example.com"
  • aud（必填）：你的 Access 应用受众标签，可通过 ctx.access.aud 读取。缺少它 Wrangler 不会启动。
  • identity（可选）：模拟已认证用户的身份声明（邮箱、姓名、用户组等），由 ctx.access.getIdentity() 返回。若 Worker 会读取用户身份就填上；若只判断 Access 是否启用，可以省略。

要换成别的用户测试，改身份字段后重启即可。要测未认证请求，删掉 dev 块——ctx.access 会变成 undefined，与生产环境中未经过 Access 的请求一致。

示例 Worker

export default {
	async fetch(request, env, ctx) {
		if (!ctx.access) {
			return new Response("Not authenticated", { status: 403 });
		}

		const identity = await ctx.access.getIdentity();
		const email = identity?.email ?? "unknown";

		return new Response(`Hello, ${email}`);
	},
};

配上上面的配置，访问 localhost:8787 会返回 Hello, admin@example.com。

身份字段

identity 对象接受任何符合生产 Access 身份结构的字段。完整列表见应用令牌——用户身份 ↗。

禁用 Access

要禁用 Worker 级或账户级 Access，打开该 Worker 的 Access 标签页或 Protect all Workers 卡片，关闭相应规则。

或者删除那个保护该 Worker、保护所有 Worker、或保护路由到该 Worker 的主机名/路径的 Access 应用。

理解 Access 的层级

一个 Worker 可能同时受多条 Access 规则保护。当多条规则都可能适用于同一个请求时，最具体的规则先生效：

  1. 基于主机名或路径的 Access：请求匹配该主机名或路径时最先适用，例如 admin.example.com 或 example.com/login。
  2. Worker 级 Access：其次适用于所选 Worker 的全部路由、自定义域名、workers.dev 主机名与预览。
  3. 账户级 Worker Access：最后作为兜底，适用于账户下所有 Worker 或所有 Worker 预览。
