本地开发

在把代码部署到 Cloudflare 网络之前，先在自己的机器上构建、运行和测试。

本地开发 原文更新于 2026-10-28 对应页面：local-development

你可以在部署到 Cloudflare 网络之前，先在自己的本地机器上构建、运行和测试 Worker 代码。这由 Miniflare 实现——它是一个模拟器，会在本地的一个 workerd ↗ 进程中执行你的 Worker 代码。托管版 Workers 平台同样由 workerd 驱动。

默认情况下，Worker 的绑定连接到本地模拟的资源；但你也可以配置远程绑定，让它们与真实的生产资源交互。

安全考量

Miniflare 不是加固过的沙箱

不要用 Miniflare 在你的机器上直接运行不可信或可能恶意的 Worker 代码。请把整个开发过程放在合适的安全沙箱里（例如虚拟机）执行。

Miniflare 会启动一个本地的 workerd ↗ 进程。这条警告适用于 wrangler dev、vite dev、vite preview 的默认本地执行、直接使用 Miniflare，以及基于 Miniflare 的测试工具。给某个绑定设置 remote: true 只改变代码访问的资源，你的 Worker 代码仍然在本地执行；相较之下，旧版的 wrangler dev --remote 是把代码放到 Cloudflare 上执行。

Miniflare 不构成针对不可信代码的安全边界。尽管 workerd 会尽量把 Worker 代码限制在配置好的资源范围内，但实现上的缺陷仍可能让代码绕过这些限制。托管版 Workers 平台有额外的纵深防御层，而 Miniflare 在本地并不提供。

核心概念

Worker 执行位置 vs 绑定

开发 Workers 时，要区分两个不同的概念：

  • Worker 执行位置：你的 Worker 代码实际在哪里运行（本地机器，还是 Cloudflare 的基础设施上）。
  • 绑定：Worker 如何与 Cloudflare 资源交互（例如 KV 命名空间 ↗、R2 存储桶 ↗、D1 数据库 ↗、Queues ↗、Durable Objects ↗等）。在 Worker 代码里，通过 env 对象访问它们（例如 env.MY_KV）。

启动本地开发服务器

有两种方式启动本地开发服务器：

1. Cloudflare Workers 的 CLI Wrangler，使用内置的 wrangler dev 命令。

npx wrangler dev
yarn wrangler dev
pnpm wrangler dev

2. Vite ↗，配合 Cloudflare Vite 插件。

npx vite dev
yarn vite dev
pnpm vite dev

Wrangler 与 Cloudflare Vite 插件底层都使用 Miniflare，并且都由 Cloudflare 团队开发维护。该选哪一个，见Wrangler 与 Vite 如何选择。

  • Wrangler 快速开始
  • Cloudflare Vite 插件快速开始

默认行为

默认情况下，运行 wrangler dev / vite dev（使用 Vite 插件时）意味着：

  • 你的 Worker 代码在本地机器上运行。
  • 在 Wrangler 配置中绑定的所有资源都在本地模拟。
  • 本地 workerd 运行时以 TZ=UTC 启动，使 Worker 中的 Date 与 Intl API 以 UTC 为准——无论你机器在哪个时区，都与生产环境一致。

本地开发时的绑定

绑定是让 Worker 与各类 Cloudflare 资源（KV 命名空间、R2 存储桶、D1 数据库、Queues、Durable Objects 等）交互的接口。在代码中通过 env 对象访问它们（如 env.MY_KV）。

本地开发时，Worker 代码调用这些绑定的 API（如 env.MY_KV.put()）与部署后完全一致。这些本地资源初始是空的，你可以往里面填数据，详见向本地资源填充数据。

  • 默认情况下，绑定连接的是本地资源模拟（AI 绑定 ↗除外——AI 模型始终在远端运行）。
  • 你可以用远程绑定逐个覆盖这一默认行为，让某个绑定连接到远程资源。这样代码仍在本地运行，但访问的是真实的生产资源。
  • 使用 wrangler dev 时，加 --local 标志（即 wrangler dev --local）可以临时禁用所有远程绑定，只连本地资源。

远程绑定

远程绑定（Remote bindings）指在本地开发期间配置为连接已部署的远程资源（而非本地模拟资源）的绑定。Wrangler、Cloudflare Vite 插件以及 @cloudflare/vitest-plugin 包都支持远程绑定。在绑定定义中设置 remote: true 即可启用。

配置示例

{
	"name": "my-worker",
	// Set this to today's date
	"compatibility_date": "2026-11-02",

	"r2_buckets": [
		{
			"bucket_name": "screenshots-bucket",
			"binding": "screenshots_bucket",
			"remote": true,
		},
	],
}
name = "my-worker"
# Set this to today's date
compatibility_date = "2026-11-02"

[[r2_buckets]]
bucket_name = "screenshots-bucket"
binding = "screenshots_bucket"
remote = true

配置远程绑定后，Worker 仍然在本地执行，变的只是绑定所连接的底层资源。对于所有标记 remote: true 的绑定，Miniflare 会把相关操作（如 env.MY_KV.put()）路由到已部署的资源；其余未显式配置的绑定继续使用默认的本地模拟。

与环境（Environments）配合

远程绑定与 Workers 环境配合得很好。为了保护生产数据，你可以建一个开发或预发（staging）环境，在 Wrangler 配置里指定与生产不同的资源。

例如：

{
	"name": "my-worker",
	// Set this to today's date
	"compatibility_date": "2026-11-02",

	"env": {
		"production": {
			"r2_buckets": [
				{
					"bucket_name": "screenshots-bucket",
					"binding": "screenshots_bucket",
				},
			],
		},
		"staging": {
			"r2_buckets": [
				{
					"bucket_name": "preview-screenshots-bucket",
					"binding": "screenshots_bucket",
					"remote": true,
				},
			],
		},
	},
}
name = "my-worker"
# Set this to today's date
compatibility_date = "2026-11-02"

[[env.production.r2_buckets]]
bucket_name = "screenshots-bucket"
binding = "screenshots_bucket"

[[env.staging.r2_buckets]]
bucket_name = "preview-screenshots-bucket"
binding = "screenshots_bucket"
remote = true

配合上面的配置运行 wrangler dev -e staging（或 CLOUDFLARE_ENV=staging vite dev），结果是：

  • Worker 代码在本地运行；
  • 对 env.screenshots_bucket 的所有调用都会使用 preview-screenshots-bucket，而不是生产的 screenshots-bucket。

推荐使用远程绑定的服务

我们建议把特定绑定配置为连接其远程对应资源。这些服务往往依赖 Cloudflare 的网络基础设施，或后端复杂，本地无法完整模拟。

建议在 Wrangler 配置中为以下绑定设置 remote: true：

Browser Run

需要与真实的无头浏览器交互来完成渲染。Browser Run 目前没有本地模拟。

{
	"browser": {
		"binding": "MY_BROWSER",
		"remote": true
	},
}
[browser]
binding = "MY_BROWSER"
remote = true

Workers AI

需要使用部署在 Cloudflare 网络上的真实 AI 模型做推理。Workers AI 目前没有本地模拟。

{
	"ai": {
		"binding": "AI",
		"remote": true
	},
}
[ai]
binding = "AI"
remote = true

Vectorize

需要连接生产环境的 Vectorize 索引，以获得准确的向量检索与相似度运算。Vectorize 目前没有本地模拟。

{
	"vectorize": [
		{
			"binding": "MY_VECTORIZE_INDEX",
			"index_name": "my-prod-index",
			"remote": true
		}
	],
}
[[vectorize]]
binding = "MY_VECTORIZE_INDEX"
index_name = "my-prod-index"
remote = true

mTLS

需要验证证书交换与校验流程确实按预期工作。mTLS 绑定目前没有本地模拟。

{
	"mtls_certificates": [
		{
			"binding": "MY_CLIENT_CERT_FETCHER",
			"certificate_id": "<YOUR_UPLOADED_CERT_ID>",
			"remote": true
			}
	]
}
[[mtls_certificates]]
binding = "MY_CLIENT_CERT_FETCHER"
certificate_id = "<YOUR_UPLOADED_CERT_ID>"
remote = true

Images

需要连接高保真版本的 Images API，确认所有变换都按预期工作。Cloudflare Images 的本地模拟只覆盖部分功能 ↗。

{
	"images": {
		"binding": "IMAGES" ,
		"remote": true
	}
}
[images]
binding = "IMAGES"
remote = true
注意

如果 Browser Run、Vectorize、mTLS 或 Images 没有指定 remote: true，Cloudflare 会给出警告，提示你考虑开启它，以获得更接近生产的测试体验。

如果 Workers AI 绑定的 remote 被设为 false，Cloudflare 会直接报错；如果省略该属性，Cloudflare 会连接远程资源，并警告你把该属性补进配置。

Dispatch Namespaces

Workers for Platforms 用户可以在 dispatch namespace 绑定定义中配置 remote: true：

{
	"dispatch_namespaces": [
		{
			"binding": "DISPATCH_NAMESPACE",
			"namespace": "testing",
			"remote":true
		}
	]
}
[[dispatch_namespaces]]
binding = "DISPATCH_NAMESPACE"
namespace = "testing"
remote = true

这样你可以在本地运行动态调度 Worker ↗，同时连接远程的 dispatch namespace 绑定，用真实部署的用户 Worker ↗来验证核心调度逻辑的改动。

不支持的远程绑定

有些绑定在本地开发时不支持远程连接（即 remote: true），它们始终使用本地模拟或本地值。

如果对下列不支持的绑定类型在 Wrangler 配置中指定 remote: true，Cloudflare 会报错。完整清单见各开发模式支持的绑定。

  • Durable Objects：未来可能支持远程连接，但目前始终在本地运行。不过，Durable Objects 与远程绑定可以配合使用，见下文配合 Durable Objects 与 Workflows 使用远程资源。
  • Workflows：同为未来可能支持，目前只在本地运行；同样可以与远程绑定配合，见下文。
  • 环境变量（vars）：环境变量本身就应该在本地与部署环境之间有所区别，在本地很容易配置（如 .dev.vars 文件或 Wrangler 配置中）。
  • 密钥（Secrets）：与环境变量同理，出于安全考虑，本地与部署环境的值本就应当不同。本地密钥请用 .dev.vars 管理。
  • 静态资源（Static Assets）：开发期间静态资源始终从本地磁盘提供，以获得速度和对改动的即时反馈。
  • 版本元数据（Version Metadata）：既然代码在本地运行，与某个已部署版本关联的版本元数据（提交哈希、版本标签等）并不适用，也不准确。
  • Hyperdrive：正在开发中，目前不支持。
  • 限流（Rate Limiting）：本地开发会话通常不应共享或影响已部署 Worker 的限流计数；限流逻辑应针对本地模拟来测。
注意

如果你确实需要连接上述远程资源，欢迎在 workers-sdk 仓库 ↗里提一个功能请求 ↗。

配合 Durable Objects 与 Workflows 使用远程资源

Durable Object 与 Workflow 绑定目前无法设为远程，但在本地开发时仍可通过它们访问远程资源。有两种推荐模式：

  • 本地 Durable Objects/Workflows + 远程绑定：在 Wrangler 配置中启用远程绑定后，本地运行的 Durable Objects 与 Workflows 就能访问远程资源。也就是说，这些绑定虽然在本地跑，却能连到远程资源。
  • 通过服务绑定访问远程 Durable Objects/Workflows：先部署一个定义了这些对象的 Worker；然后在本地 Worker 中配置一个指向该已部署 Worker 的远程服务绑定。本地 Worker 即可与远程 Worker 交互，后者再与远程的 Durable Objects/Workflows 通信。用这种方式，你相当于把已部署的 Worker 当作代理接口，在本地开发期间借它访问远程绑定。

重要注意事项

  • Cloudflare Access：如果你的 Worker 受 Cloudflare Access 保护，Wrangler 在连接远程绑定时必须通过 Access 认证。参见连接受 Access 保护的 Worker。
  • 数据修改：对远程连接绑定的操作（写、删、改）会影响目标 Cloudflare 资源中的真实数据（无论是预览还是生产）。
  • 计费：通过这些连接与远程 Cloudflare 服务交互，会产生该服务的标准运营费用（如 KV 操作、R2 存储与操作、AI 请求、D1 用量）。
  • 网络延迟：远程连接的绑定涉及互联网通信，操作会有网络延迟。

连接受 Access 保护的 Worker

如果 Worker 受 Cloudflare Access 保护，Wrangler 在连接远程绑定时必须先通过 Access 认证。无论 Access 保护的是 Worker 本身、账户下所有 Workers、workers.dev 主机名、自定义域名，还是其他路由到该 Worker 的主机名或路径，都适用。

有两种认证方式：

  • 交互式登录（本地开发）：如果已定义接受用户登录的策略，Wrangler 会在浏览器中启动交互式的 cloudflared access login 流程。除了登录正确账号，无需其他设置。若策略只允许服务令牌认证，Wrangler 会跳过交互流程并报错，提示需要服务令牌凭据。
  • 服务令牌（CI / 非交互环境）：在 CI/CD 流水线等非交互场景，或策略只允许服务令牌认证时，Wrangler 无法启动浏览器交互流程，必须改用 Cloudflare Access 服务令牌 ↗。非交互环境下若未配置服务令牌，Wrangler 会直接报错，而不是尝试交互流程。

配置服务令牌认证的步骤：

1. 创建服务令牌。在 Cloudflare 控制台进入 Zero Trust > Access > Service Auth > Service Tokens，新建一个令牌。完整说明见服务令牌文档 ↗。界面会给出 Client ID 与 Client Secret——请妥善保存，secret 不会再次显示。

2. 给保护 Worker 的 Access 应用加上 Service Auth 策略。打开已有的那个保护 Worker（或你用于远程绑定的主机名）的 Access 应用，附加一条新策略：

  • Action：Service Auth
  • Include：你刚创建的服务令牌；如果你希望任何服务令牌都能访问，则选 "Any Access Service Token"。
谨慎

不要为了添加服务令牌认证而给同一个 Worker 或主机名另建一个 Access 应用——这会与已保护该 Worker 的应用冲突。请把 Service Auth 策略附在已有应用上。

3. 让 Wrangler 拿到凭据。在运行 Wrangler 的环境中设置 CLOUDFLARE_ACCESS_CLIENT_ID 与 CLOUDFLARE_ACCESS_CLIENT_SECRET 这两个系统环境变量：

export CLOUDFLARE_ACCESS_CLIENT_ID=<CLIENT_ID>
export CLOUDFLARE_ACCESS_CLIENT_SECRET=<CLIENT_SECRET>

在 CI 中，把这两个值存为 secret，并在运行 Wrangler 的步骤里以环境变量形式暴露。

API

Wrangler 提供了一些编程接口，方便工具作者在使用 Miniflare 运行 Worker 代码时支持远程绑定连接。

主要 API：

  • startRemoteProxySession：启动一个可与远程绑定交互的代理会话。
  • unstable_convertConfigBindingsToStartWorkerBindings：转换绑定定义的工具函数。
  • experimental_maybeStartOrUpdateProxySession：便捷启动或更新代理会话的函数。

startRemoteProxySession

为给定的一组绑定启动代理会话。它接受控制会话行为的选项，其中包括 auth（你的 Cloudflare 账户 ID 与 API 令牌，用于远程绑定访问）。

返回一个对象，包含：

  • ready Promise<void>：会话就绪时 resolve。
  • dispose () => Promise<void>：停止会话。
  • updateBindings (bindings: StartDevWorkerInput['bindings']) => Promise<void>：更新会话绑定。
  • remoteProxyConnectionString：传给 Miniflare 以访问远程绑定的连接字符串。

unstable_convertConfigBindingsToStartWorkerBindings

unstable_readConfig 工具返回一个 Unstable_Config 对象，其中包含配置文件里的绑定定义。但这些定义并不能直接被 startRemoteProxySession 使用。先用 unstable_readConfig 读出绑定声明、再喂给 startRemoteProxySession，是很自然的用法，因此 Wrangler 提供了 unstable_convertConfigBindingsToStartWorkerBindings，把 Unstable_Config 对象中的绑定转换成可传给 startRemoteProxySession 的结构。

注意

这个类型转换是临时的。未来类型会统一，届时可以直接把配置对象传给 startRemoteProxySession。

maybeStartOrUpdateRemoteProxySession

这个包装函数简化了代理会话的管理。它接受：

  • 一个对象，其内容为下列之一：
    • Wrangler 配置文件的路径，以及可能的目标环境；
    • Worker 的名称，以及它使用的绑定。
  • 当前代理会话的详情（没有会话时可传 null 或不传）。
  • 可能需要的、用于远程代理会话的认证数据。

如果会话已启动或已更新，返回带有代理会话详情的对象；如果不需要代理会话，返回 null。

具体行为：

  • 根据第一个参数准备代理会话的入参。
  • 如果没有要使用的远程绑定（也没有既有会话），返回 null，表示不需要代理会话。
  • 如果传入了现有会话的详情，则据此更新该会话。
  • 否则启动一个新的代理会话。
  • 返回会话详情（之后可作为第二个参数再传回 maybeStartOrUpdateRemoteProxySession）。

示例

下面是一个基础示例：用 Miniflare 配合 maybeStartOrUpdateRemoteProxySession，搭出一个带远程绑定的本地开发会话。示例中硬编码了一个 KV 绑定。

import { Miniflare, MiniflareOptions } from "miniflare";
import { maybeStartOrUpdateRemoteProxySession } from "wrangler";

let mf;

let remoteProxySessionDetails = null;

async function startOrUpdateDevSession() {
	remoteProxySessionDetails = await maybeStartOrUpdateRemoteProxySession(
		{
			bindings: {
				MY_KV: {
					type: "kv_namespace",
					id: "kv-id",
					remote: true,
				},
			},
		},
		remoteProxySessionDetails,
	);

	const miniflareOptions = {
		scriptPath: "./worker.js",
		kvNamespaces: {
			MY_KV: {
				id: "kv-id",
				remoteProxyConnectionString:
					remoteProxySessionDetails?.session.remoteProxyConnectionString,
			},
		},
	};

	if (!mf) {
		mf = new Miniflare(miniflareOptions);
	} else {
		mf.setOptions(miniflareOptions);
	}
}

// ... tool logic that invokes `startOrUpdateDevSession()` ...

// ... once the dev session is no longer needed run
// `remoteProxySessionDetails?.session.dispose()`

> | null = null;

wrangler dev --remote（旧版）

除了由 Miniflare 驱动的本地开发，Wrangler 还提供一种完全远程的开发模式：wrangler dev --remote。远程开发不被 Vite 插件支持。

npx wrangler dev --remote
yarn wrangler dev --remote
pnpm wrangler dev --remote

在远程开发模式下，你的 Worker 代码会被上传到 Cloudflare 基础设施上的一个临时预览环境，代码一保存就会自动上传。

这种方式下，所有绑定都会自动连接远程资源。与本地开发不同，你无法把绑定配置为使用本地模拟——它们始终使用 Cloudflare 网络上已部署的资源。

什么时候用远程开发

  • 大多数开发任务，最高效的体验是本地开发，需要时再叠加远程绑定。
  • 当你需要测试高度依赖 Cloudflare 网络、既难以在本地模拟、也无法通过远程绑定验证的特性或行为时，可以用 wrangler dev --remote。

注意事项

  • 因为每次改动都要上传或部署，迭代速度明显慢于本地开发。

  • 用 --remote 运行远程开发会话时，每个区域最多 50 条路由（routes）。详见 Workers 平台限额。
  • Python Worker 不支持 --remote，请改用远程绑定。
