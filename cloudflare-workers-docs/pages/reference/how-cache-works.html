缓存的工作机制

Workers 如何与 Cloudflare 缓存交互，以及清理缓存时该清哪个 URL。

参考 原文更新于 2026-10-29 对应页面：reference/how-the-cache-works

Workers 构建在 Cloudflare 的全球网络之上，目的之一就是让开发者能够直接操作 Cloudflare 缓存。缓存可以提供临时性的、数据中心本地的存储，是频繁访问静态或动态内容时的一种便利手段。

通过允许开发者写入缓存，Workers 提供了一种在 Cloudflare CDN 上自定义缓存行为的方式。缓存有哪些好处，参见学习中心的《什么是缓存？》↗。

Cloudflare Workers 在缓存之前运行，但也可以用来修改从缓存返回的资源。修改从缓存返回的资源，意味着你既能对响应签名或个性化，又能减少源站压力、并通过就近分发资源降低终端用户的延迟。

注意

本页讲的是 Workers 如何与某个区域（zone）的 Cloudflare 缓存交互——例如 Worker 运行在配置了 Cache Rules 的区域上，或 Worker 使用 Cache API 或 fetch() 存取响应时。

如果你想缓存的是 Worker 自身的响应（让 Cloudflare 直接返回缓存结果、不再执行 Worker），请参阅 Workers 缓存。

与 Cloudflare 缓存交互

从概念上讲，用 Worker 与 Cloudflare 缓存交互有两种方式：

  • 在 Workers 脚本中调用 fetch()。经由 Cloudflare 代理的请求，即便没有 Workers，也会按区域的默认或配置行为被缓存（例如 .jpg 结尾的静态文件默认就会被缓存）。Worker 还能进一步定制这一行为：
    • 设置 Cloudflare 缓存规则（也就是操作请求上的 cf 对象）。
  • 在 Workers 脚本中用 Cache API 存储响应。这样可以缓存并非来自源站的响应，并通过下面两点获得更细的控制：
    • 给传给 cache.put() 的响应设置 Cache-Control 等响应头，从而定制任意资源的缓存行为。
    • 用 cache.put() 缓存 Worker 自己生成的响应。
分层缓存（Tiered caching）

Cache API 与分层缓存不兼容。要用分层缓存，请改用 fetch API。

清理由 Worker 缓存的单个文件

用单文件清理（single-file purge）清理由 Worker 缓存下来的资源时，注意不要在清理时使用终端用户的 URL，而要清理 fetch 请求里那个 URL。举例来说：你有一个运行在 https://example.com/hello 的 Worker，它向 https://notexample.com/hello 发起 fetch 请求。

就缓存而言，被缓存的是 fetch 请求里的资源（https://notexample.com/hello）。要清理它，就得清理 https://notexample.com/hello。

清理终端用户 URL https://example.com/hello 不会生效，因为缓存看到的不是这个 URL。你需要在 Worker 里确认实际抓取的是哪个 URL，才能清对资源。

在上面的例子里，https://notexample.com/hello 没有经过 Cloudflare 代理。如果它经过了代理（橙云代理 ↗），那你就必须拥有 notexample.com，并从 notexample.com 这个区域清理 https://notexample.com/hello。

清理通过 Cache API 存储的资源

通过 Cache API 存入缓存的资源，有几种清理方式：

  • 在 Worker 内调用 cache.delete，用匹配的 request 变量使该资源的缓存失效。
    • 这样清理只影响本地——仅限执行该 Worker 运行时的那个数据中心。
  • 要全局清理，请使用标准的缓存清理选项 ↗。受 Cache API 实现所限，并非所有清理端点都能清理 Cache API 存入的资源。
    • 用 Purge Everything ↗ 可以清理某个区域上的全部资源。这次清理会把该 Cloudflare 区域关联的所有资源从所有数据中心的缓存中移除，无论当初用的是什么方法存入。
    • Cache Tags ↗ 可以在 Worker 里动态加到请求上：调用 response.headers.append() 把 Cache-Tag 值动态附加到该请求。设置好之后，就能用这些标签有选择地清理资源，而不必让整个区域的缓存全部失效。注意 cache.match() 返回的响应不含 Cache-Tag；如果你要把匹配到的响应重新存入，请在调用 put() 之前先设置 Cache-Tag。更多细节见 Put。
  • 目前还无法清理使用了 Worker 自定义缓存键的 URL。可以改用通过 Cache Rules 创建的自定义键 ↗；或者改用 purge everything、按标签清理、按主机清理、按前缀清理来清理资源。

边缘缓存与浏览器缓存

浏览器缓存由响应中发给客户端的 Cache-Control 头控制（那个响应就是处理器返回的 Response 实例）。Worker 通过在响应上设置这个头来定制浏览器缓存行为。

本文未提及的其他缓存控制手段还有：Page Rules 与 Cloudflare 缓存设置。如果你不想写 JavaScript、又希望保留一定粒度的控制，参见如何自定义 Cloudflare 缓存 ↗。

该用 Cache API 还是 fetch 来缓存对象？

当 Worker 扮演中间件角色（即通过 fetch 发起子请求）时，推荐使用 fetch。因为已有现成设置会在优化缓存的同时，避免意外的动态缓存。对于没有后端的项目（即整个项目都在 Workers 上，例如 Workers Sites），Cache API 是定制缓存的唯一选择。

资源会被缓存到 Worker 子请求中指定的主机名下，而不是 Worker 自己的主机名。因此要清理这份缓存，必须针对子请求里包含的那个主机名执行清理。

fetch

在 Workers 语境中，运行时提供的 fetch 会与 Cloudflare 缓存通信。首先，fetch 检查该 URL 是否属于另一个区域：如果属于，就走那个区域的缓存（或 Worker）；否则走自己区域的缓存——即便该 URL 指向的是非 Cloudflare 的站点。基于你的 Cloudflare 设置，fetch 会自动套用相应的缓存规则。fetch 不允许你在对象进入缓存之前修改或检视它，但允许你决定它将如何被缓存。

当一次响应填充了缓存，其响应头会包含 CF-Cache-Status: HIT。只要能看到 CF-Cache-Status，就说明该对象正在尝试走缓存。

Cache API

Cache API 可以看成一个临时的键值存储：Request 对象（更准确地说，是请求 URL）是键，Response 是值。

Cloudflare 缓存提供两种缓存命名空间：

  • caches.default：访问默认缓存（与 fetch 请求共用的同一份缓存）。当你需要在收到响应后覆盖已被缓存的内容时很有用。
  • caches.open()：用 let cache = await caches.open(CACHE_NAME) 访问一个带命名空间的缓存（与 fetch 共用的缓存相互独立）。注意 caches.open ↗ 是异步函数，而 caches.default 不是。

什么时候用 Cache API：

  • 当你需要以编程方式向缓存保存或删除响应时。比如源站返回 Cache-Control: max-age:0 且无法改动，你可以克隆这个 Response，把头改成 max-age=3600，再用 Cache API 把修改后的响应缓存一小时。
  • 当你需要以编程方式从缓存读取响应、而不依赖 fetch 请求时。比如先检查 https://example.com/slow-response 的响应是否已缓存；如果已缓存，就能避开那个慢请求。

分层缓存与 Cache API

Workers 中的 Cache API 不支持分层缓存。分层缓存会把到源站的连接集中起来，使其来自少数几个数据中心，而不是全部网络位置。而 Cache API 是数据中心本地的：cache.match 查找、cache.put 存储、cache.delete 删除，都只在处理该请求的 Worker 所在数据中心的缓存中生效。因为这些方法只作用于本地缓存，所以无法与分层缓存配合。
