从 Service Worker 迁移到 ES Modules

把 Worker 从 Service Worker 写法改成 ES modules 写法，换取更快的执行与更多能力。

参考 原文更新于 2026-07-03 对应页面：reference/migrate-to-module-workers

本指南演示如何把 Worker 从 Service Worker ↗ 格式迁移到 ES modules ↗ 格式。

迁移的好处

把 Worker 迁到 ES modules 格式，有几个原因：

  1. 运行更快。Service Worker 写法把绑定暴露成全局变量，这意味着每个请求都必须创建一个新的 JavaScript 执行上下文，增加开销与耗时；用 ES modules 写的 Worker 可以在多个请求间复用同一个执行上下文。
  2. 实现 Durable Objects ↗ 要求 Worker 使用 ES modules。
  3. D1 ↗、Workers AI ↗、Vectorize ↗、Workflows ↗、Images ↗ 的绑定只能在 ES modules 写的 Worker 中使用。
  4. 使用 ES modules 格式时，你可以渐进式部署改动。
  5. 可以方便地把 ES modules 格式的 Worker 发布到 npm，从而在代码库中导入、复用。

迁移一个 Worker

下面的例子是一个把所有入站请求以 301 状态码重定向到某个 URL 的 Worker。

Service Worker 写法已废弃

Service Worker 写法已废弃，但仍然受支持。我们建议改用 模块化 Worker（Module Workers）。新特性可能不再支持 Service Worker 写法。

用 Service Worker 语法，这个例子的写法是：

async function handler(request) {
  const base = 'https://example.com';
  const statusCode = 301;

  const destination = new URL(request.url, base);
  return Response.redirect(destination.toString(), statusCode);
}

// Initialize Worker
addEventListener('fetch', event => {
  event.respondWith(handler(event.request));
});

用 ES modules 格式的 Worker 把 addEventListener 语法换成对象定义，该对象必须是文件的默认导出（export default）。上面的代码变成：

export default {
  fetch(request) {
    const base = "https://example.com";
    const statusCode = 301;

    const source = new URL(request.url);
    const destination = new URL(source.pathname, base);
    return Response.redirect(destination.toString(), statusCode);
  },
};

绑定

绑定让 Worker 能与 Cloudflare 开发者平台上的资源交互。

ES modules 格式的 Worker 不依赖任何全局绑定；而 Service Worker 语法是从全局作用域上取绑定的。

为了讲清楚绑定，下面以 TODO 这个 KV 命名空间绑定为例。创建该绑定需要：

  1. 创建一个名为 My Tasks 的 KV 命名空间，拿到一个 ID，稍后用于绑定。
  2. 创建一个 Worker。
  3. 找到 Worker 的 Wrangler 配置文件，加上 KV 命名空间绑定：
{
	"kv_namespaces": [
		{
			"binding": "TODO",
			"id": "<ID>"
		}
	]
}
[[kv_namespaces]]
binding = "TODO"
id = "<ID>"

下面两节分别演示在 Service Worker 与 ES modules 格式中如何使用这个绑定。

从 Durable Objects 与 Workers 中引用 KV

想了解如何在 Worker 中引用 KV，参见 KV 绑定文档 ↗。

Service Worker 格式中的绑定

在 Service Worker 语法里，TODO 这个 KV 命名空间绑定定义在 Worker 的全局作用域上，应用代码的任何位置都能直接用。

addEventListener("fetch", async (event) => {
  return await getTodos()
});

async function getTodos() {
  // Get the value for the "to-do:123" key
  // NOTE: Relies on the TODO KV binding that maps to the "My Tasks" namespace.
  let value = await TODO.get("to-do:123");

  // Return the value, as is, for the Response
  event.respondWith(new Response(value));
}

ES modules 格式中的绑定

在 ES modules 格式中，绑定只在 Worker 入口处提供的 env 参数里可用。

要在代码里访问 TODO 这个 KV 命名空间绑定，必须把 env 参数从 Worker 的 fetch 处理器传到 getTodos 函数。

import { getTodos } from './todos'

export default {
  async fetch(request, env, ctx) {
    // Passing the env parameter so other functions
    // can reference the bindings available in the Workers application
    return await getTodos(env)
  },
};

下面这个 getTodos 函数在 TODO 这个 KV 绑定上调用了 get。

async function getTodos(env) {
  // NOTE: Relies on the TODO KV binding which has been provided inside of
  // the env parameter of the `getTodos` function
  let value = await env.TODO.get("to-do:123");
  return new Response(value);
}

export { getTodos }

环境变量

ES modules 格式与 Service Worker 格式在代码中访问环境变量的方式不同。

先看下面的环境变量配置（位于 Wrangler 配置文件）：

{
	"$schema": "./node_modules/wrangler/config-schema.json",
	"name": "my-worker-dev",
	// Define top-level environment variables
	// using the {"vars": "key": "value"} format
	"vars": {
		"API_ACCOUNT_ID": "<EXAMPLE-ACCOUNT-ID>"
	}
}
"$schema" = "./node_modules/wrangler/config-schema.json"
name = "my-worker-dev"

[vars]
API_ACCOUNT_ID = "<EXAMPLE-ACCOUNT-ID>"

Service Worker 格式中的环境变量

在 Service Worker 格式中，API_ACCOUNT_ID 定义在 Worker 应用的全局作用域上，代码任何位置都能用。

addEventListener("fetch", async (event) => {
  console.log(API_ACCOUNT_ID) // Logs "<EXAMPLE-ACCOUNT-ID>"
  return new Response("Hello, world!")
})

ES modules 格式中的环境变量

在 ES modules 格式中，环境变量通过 Worker 应用入口处提供的 env 参数访问：

export default {
  async fetch(request, env, ctx) {
    console.log(env.API_ACCOUNT_ID) // Logs "<EXAMPLE-ACCOUNT-ID>"
    return new Response("Hello, world!")
  },
};

你也可以从 cloudflare:workers 导入 env，从而在代码的任何位置（包括顶层作用域）访问环境变量：

import { env } from "cloudflare:workers";

// Access environment variables at the top level
const accountId = env.API_ACCOUNT_ID;

export default {
	async fetch(request) {
		console.log(accountId); // Logs "<EXAMPLE-ACCOUNT-ID>"
		return new Response("Hello, world!");
	},
};
import { env } from "cloudflare:workers";

// Access environment variables at the top level
const accountId = env.API_ACCOUNT_ID;

export default {
  async fetch(request: Request): Promise<Response> {
    console.log(accountId) // Logs "<EXAMPLE-ACCOUNT-ID>"
    return new Response("Hello, world!")
  },
};

这种做法适合在初始化配置时使用，也适合从深层嵌套的函数里访问环境变量，而无需在每次函数调用时层层传递 env。更多细节见把 env 作为全局导入。

Cron 触发器

要在 ES modules 语法的 Worker 里处理 Cron 触发器事件，请实现 scheduled() 事件处理器，它相当于 Service Worker 语法里监听 scheduled 事件。

下面这段代码：

addEventListener("scheduled", (event) => {
  // ...
});

变成：

export default {
  async scheduled(event, env, ctx) {
    // ...
  },
};

访问 event 或 context 上的数据

Worker 经常需要访问 request 对象之外的数据。例如有时会用 waitUntil 延迟执行。ES modules 格式的 Worker 通过 context 参数访问 waitUntil。更多信息见 ES modules 参数说明。

下面这段代码：

async function triggerEvent(event) {
  // Fetch some data
  console.log('cron processed', event.scheduledTime);
}

// Initialize Worker
addEventListener('scheduled', event => {
  event.waitUntil(triggerEvent(event));
});

变成：

async function triggerEvent(event) {
  // Fetch some data
  console.log('cron processed', event.scheduledTime);
}

export default {
  async scheduled(event, env, ctx) {
    ctx.waitUntil(triggerEvent(event));
  },
};

Service Worker 语法

用 Service Worker 语法写的 Worker 由两部分组成：

  1. 一个监听 FetchEvents 的事件监听器；
  2. 一个事件处理器，返回的 Response 对象会传给事件的 .respondWith() 方法。

当某个匹配该 Worker 的 URL 请求抵达 Cloudflare 全球网络上的服务器时，Cloudflare 的服务器会把请求交给 Workers 运行时，从而在 Worker 所在的 isolate 中派发一个 FetchEvent。

addEventListener('fetch', event => {
  event.respondWith(handleRequest(event.request));
});

async function handleRequest(request) {
  return new Response('Hello worker!', {
    headers: { 'content-type': 'text/plain' },
  });
}

下面是这套请求响应流程的说明：

  1. 针对 FetchEvent 的事件监听器告诉脚本：监听所有抵达该 Worker 的请求。监听器会收到 event 对象，其中包含 event.request——一个 Request 对象，代表触发该 FetchEvent 的 HTTP 请求。
  2. 调用 .respondWith() 让 Workers 运行时拦截该请求，并返回自定义响应（本例中是纯文本 'Hello worker!'）。
    • FetchEvent 处理器通常最终会以 .respondWith() 收尾，传入 Response 或 Promise<Response> 来决定响应。
    • FetchEvent 对象还提供另外两个方法，用于处理意外异常，以及在响应返回之后才完成的操作。

进一步了解 fetch() 处理器的生命周期方法。

受支持的 FetchEvent 属性

  • event.type（string）：事件类型，始终返回 "fetch"。
  • event.request（Request）：传入的 HTTP 请求。
  • event.respondWith(response: Response | Promise)：void，见respondWith。
  • event.waitUntil(promise: Promise)：void，见 waitUntil。
  • event.passThroughOnException()：void，见 passThroughOnException。

respondWith

拦截请求，让 Worker 能够返回自定义响应。

如果某个 fetch 事件处理器没有调用 respondWith，运行时会把这个事件交给下一个注册的 fetch 事件处理器。换句话说，虽然不推荐，但你确实可以在一个 Worker 里放多个 fetch 事件处理器。

如果所有 fetch 事件处理器都没有调用 respondWith，运行时会把请求转发给源站，就像没有这个 Worker 一样。但如果没有源站——或者这个 Worker 本身就是你的源站（对 *.workers.dev 域名来说总是如此）——那么你必须调用 respondWith，才能得到有效响应。

// Format: Service Worker
addEventListener('fetch', event => {
  let { pathname } = new URL(event.request.url);

  // Allow "/ignore/*" URLs to hit origin
  if (pathname.startsWith('/ignore/')) return;

  // Otherwise, respond with something
  event.respondWith(handler(event));
});

waitUntil

waitUntil 会延长 "fetch" 事件的生命周期。它接受一个基于 Promise 的任务，Workers 运行时会在这个处理器结束前执行它，同时不阻塞响应。例如，这很适合用来缓存响应或处理日志。

在 Service Worker 格式里，waitUntil 就在 event 上，因为它是 FetchEvent 的原生属性。

在 ES modules 格式里，waitUntil 挪到了 context 参数对象上。

// Format: Service Worker
addEventListener('fetch', event => {
  event.respondWith(handler(event));
});

async function handler(event) {
  // Forward / Proxy original request
  let res = await fetch(event.request);

  // Add custom header(s)
  res = new Response(res.body, res);
  res.headers.set('x-foo', 'bar');

  // Cache the response
  // NOTE: Does NOT block / wait
  event.waitUntil(caches.default.put(event.request, res.clone()));

  // Done
  return res;
}

passThroughOnException

当 Worker 抛出未处理的异常时，passThroughOnException 方法可以避免返回一个运行时错误响应，转而让脚本失效放行（fail open）↗，把请求代理到源站，就像这个 Worker 从未被调用过。

为了避免 JavaScript 错误在未捕获异常时导致整个请求失败，passThroughOnException() 会让 Workers 运行时把控制权交给源站。

在 Service Worker 格式里，passThroughOnException 被加到 FetchEvent 接口上，因此在 event 上可用。

在 ES modules 格式里，passThroughOnException 位于 context 参数对象上。

// Format: Service Worker
addEventListener('fetch', event => {
  // Proxy to origin on unhandled/uncaught exceptions
  event.passThroughOnException();
  throw new Error('Oops');
});
